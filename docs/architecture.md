# 执行流程与设计选择

对应 0.3.0。这个应用围绕个人工作区运行，前端为原生 JavaScript，后端为 FastAPI 和 SQLite。

## 一次任务怎样执行

1. 浏览器提交任务和请求编号，服务端校验参数与会话，创建 run。
2. RunManager 启动异步任务，浏览器通过 GET SSE 接收事件。
3. Engine 构建上下文、接收模型流，按 index 合并工具调用分片，再校验名称与 JSON 参数。
4. 工具执行结果写入会话，再返回模型。程序限制总时限、轮次与调用数。
5. 回复、工具状态和结束事件存入 SQLite；页面刷新后从事件流重新接收。

请求编号用于去重；同一会话只允许一个运行中的任务。浏览器断线与任务取消是两个操作：断线停止接收，取消接口才通知后台任务停止。

## 为什么分开保存消息、任务和事件

消息用于恢复对话；run 表达执行状态和请求去重；事件支持页面重接与工具过程回看。只有页面上的文字不足以恢复一次中断中的执行。

服务启动时用数据库文件锁保证单实例，并把没有结束的 run 恢复为中断状态。已记录的内容保留，不自动重跑带副作用的操作。

## 文件上传怎样进入模型上下文

上传接口接收原文件，检查大小、格式和路径。文本统一编码；PDF/DOCX 在单独解析进程中提取正文，原文件与正文分开保存。页面保存引用，用户发送任务后模型才会读取相应文件。

解析有超时、展开大小和输出限制，Linux 还设置资源上限。扫描件不进行 OCR。模型读取的是提取文字，复杂表格、公式和图片需要核对原文件。

## 如何核对文件改动

RunManager 用 ContextVar 绑定当前任务。write_file/edit_file 在应用写锁内运行：先保存 pending 记录，再执行操作，最后重新读取文件，保存前后 SHA-256、大小及有界文本差异。

文件系统与 SQLite 不是一个原子事务。pending 明确表示最终状态尚未确认；取消和异常仍会尽量记录已经发生的修改。哈希只用于比较文件字节是否一致，不判断内容质量。

报告分别统计工具事件和文件变化。页面查看时重新核对当前文件，显示后续编辑、删除或不可读取状态。当前界面显示最近一次任务的记录，各任务的报告按 run_id 保存在服务端，可导出 JSON。

该记录目前仅覆盖本版任务经 write_file/edit_file 发起的操作。手动上传、编辑和外部程序不计为本次任务的写入；没有自动回滚。

## 当前取舍

- 原生前端：页面状态和 SSE 协议可以直接追踪；当前规模不需要额外框架。
- SQLite：适合当前单机实践；未通过负载测试承诺高并发能力。
- 单进程与异步任务：应用内管理取消、去重和重接；尚未引入分布式任务队列。
- 上下文按完整轮次选择，避免工具调用与结果被拆开；当前是字符和消息预算，不是精确 token 预算。
- 受限文件与查看工具：应用层控制路径、命令适配器和网络目标；未配置通用代码运行环境。

这些取舍便于继续验证执行流程。后续可以围绕长文档分段检索、来源定位、历史任务入口和固定任务评估逐项完善。
